# 智能客服 Agent

一个可运行的电商智能客服系统：多轮对话、知识库检索、意图识别、自动转人工、对话持久化、数据看板。
纯前端实现，**零后端即可上线**，同时支持一键切换为「真大模型 + 真云数据库」生产模式。

| | 地址 | 说明 |
|---|---|---|
| 客服对话端 | https://6060e0dab2c14d1fb09d2bafec178379.app.workbuddy.host | 直接对话体验 |
| 管理后台 | 同上 `/admin.html` | 访问口令 `admin2026` |

> 后台首次打开是空的，点右上角 **「生成演示数据」** 可一键造 30 个会话 / 7 天历史，看板立刻有数据。

## 二、技术架构

```
用户提问
  │
  ├─① 意图识别（三层融合）──────────────────────────────┐
  │    规则快通道(0.45) + FAQ检索信号(0.30) + 大模型分类(0.25)
  │    → 加权投票 + 一致性加成 + 上下文修正 + 负向抑制
  │
  ├─② 槽位填充（Slot Filling）
  │    按意图 schema 检查必填项（如查订单必须订单号）
  │    缺失则追问，超过重试上限 → 转人工
  │
  ├─③ 回答生成（RAG）
  │    BM25 检索 → 提示词拼装 → DeepSeek 生成
  │    无 Key / 调用失败 → 回落知识库原文（永远有答案）
  │
  ├─④ 兜底与转人工
  │    低置信 / 负面情绪 / 投诉 / 连续未理解 → 生成工单落库
  │
  └─⑤ 全链路埋点
       每条消息记录 意图/置信度/来源/耗时 → 后台统计分析
```

## 三、算法设计要点

### 3.1 三层融合意图识别

单层方案的短板很明显：纯规则泛化差，纯 LLM 有延迟和成本，纯检索依赖知识库覆盖。
因此采用加权投票，且**任一层缺失时权重自动重分配**，保证无 Key 时仍是完整的两层融合。

```
score(intent) = Σ layer_score × layer_weight / Σ 有效权重
              + 一致性加成（多层 top1 相同 +0.12）
              + 上下文继承（上一轮主题 +0.15，纯槽位值 →0.92）
              − 负向抑制（跨意图误命中 ×0.3）
```

负向抑制解决了一个真实问题：「退款什么时候到账」里的「什么时候到」会命中物流意图的强规则，
命中排除词后物流分数衰减到 30%，最终正确判为退款。

### 3.2 检索：BM25 + 三重调优

- **中文 bigram 切分**：不依赖分词器，对短 query 效果好，离线可跑
- **查询类型感知重排序**：用户问「怎么退款」是求流程，说「退款失败」是报故障，两者该命中的条目完全不同。
  按类型双向调整（匹配 +0.28 / 不匹配 −0.18），解决了「这个能退款吗」被「退款被拒怎么办」抢走的 badcase
- **绝对质量门**：相对归一化会把无关查询也拉到高分，因此用「有效分 = BM25 × 覆盖率系数」做门控，
  并以 `min(1, (score/4.0)²)` 平方衰减。门控作用在最终分上——否则字面/关键词加分会绕过它

### 3.3 转人工：5 种触发策略

显式要求人工、投诉维权、强烈负面情绪、极低置信且无知识库支撑、连续 N 轮未理解。
关键设计是**知识库强命中豁免**：口语化表达（如「券用不上咋回事」）置信度天然偏低，
但只要检索到高相关条目就不转人工——否则人工坐席会被正常咨询淹没。

### 3.4 永远可降级

LLM 未配置 / 超时 / 报错 → 回落知识库原文；知识库也未命中 → 兜底澄清话术并给出候选问题。
任何一层故障都不会导致对话中断，这是客服系统的底线。

## 四、数据模型（4 张表）

| 表 | 作用 | 关键字段 |
|---|---|---|
| `sessions` | 一次对话 | status、transferred、message_count |
| `messages` | 每一轮对话，分析的基础 | role、**intent、confidence、source、latency_ms** |
| `tickets` | 转人工工单 | reason、category、priority、status |
| `feedbacks` | 满意度 | score(1-5)、comment |

`messages` 表把意图、置信度、回答来源、耗时全部落库，这是后台能做出
「意图分布 / 自动化解决率 / 回答来源构成 / 响应时长」的原因。

## 五、快速开始

```bash
# 本地预览（不要直接双击 html，浏览器会限制 file:// 下的 localStorage）
node deploy/serve-local.js 8123
# 客服端 http://localhost:8123/index.html
# 后台   http://localhost:8123/admin.html   （口令 admin2026）
```

**接入大模型（可选）**：客服端右上角「设置」填 DeepSeek Key。
官方端点没有 CORS 头，浏览器直连会被拦，需配反代：

```bash
node deploy/proxy-node.js          # 本地：反代地址填 http://localhost:8787/v1
# 线上：把 deploy/worker-proxy.js 部署到 Cloudflare Workers
```

**接入云数据库（可选）**：
1. 建 Supabase 项目 → SQL Editor 执行 `sql/schema.sql`
2. 设置里填 Project URL 和 anon key → 数据即从浏览器写入云端 Postgres

不填任何 Key 也能完整运行，此时为「内置规则引擎 + localStorage」演示模式。

```bash
node test/smoke.js            # 意图识别 26 例 + 多轮对话 + 转人工 5 场景 + 落库校验
node test/eval-retrieval.js   # 检索器离线评估（正例 154 条 + 负例 14 条）

```

当前指标：

| 指标 | 结果 |
|---|---|
| 意图识别准确率 | **26/26 = 100%**（含 8 条口语化变体） |
| 检索 Top1（标准问法，139 条） | **100%** |
| 检索 Top1（口语化，15 条） | **93.3%** |
| 无关问题拦截率 | **92.9%** |
| 转人工策略 | 5 种场景全部符合预期 |
| 浏览器冒烟 | 全绿，无运行时错误 |

> 超参（`absFloor=4.0 / power=2 / 阈值=0.45`）由 `test/tune.js` 在
> 6×5×4=120 组组合中扫描得出，不是拍脑袋定的。改参数前请先重跑扫描。

## 七、已知限制

| 限制 | 说明 | 生产改进方向 |
|---|---|---|
| Key 在前端 | 纯静态部署的固有问题 | Key 存服务端/边缘函数环境变量，前端只带短期令牌 |
| 后台口令鉴权 | 演示级保护 | 接 Supabase Auth 或 JWT |
| 订单数据为模拟 | 无真实业务系统 | 替换 `agent.js` 的 `mockOrderQuery` 为后端接口 |
| 检索为词法匹配 | 未用向量，同义词召回有上限 | 引入 embedding 做向量召回，与 BM25 混合 |
